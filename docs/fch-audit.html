Security & Engineering Audit

FCH Platform Audit

A verified review of the three FCH repositories. Eight critical security defects, two builds that ship broken, no automated tests and no CI quality gate. This is a US lending platform holding SSNs, credit-bureau data and payment credentials — several findings are live regulatory exposure, not hypothetical risk.

PHASE 0

Emergency

Do first

These are exploitable or actively failing right now. Everything else waits.

0.1

Runaway session hook is spawning processes

My bug

The SessionEnd hook I added last session calls claude --resume, which starts a new session; that session's exit fires SessionEnd again. Unbounded recursion.

client-fch/docs/handoff/ — 516 files, all 0 bytes one every ~2s · ~258 per session · claude + node processes still live

Files are empty because the script is killed before its [ -s "$out" ] || rm -f cleanup ever runs.

  • Kill the live processes, delete the 516 files, gitignore docs/handoff/.
  • Add a re-entry guard and a repo-keyed lockfile — an env guard alone won't hold, since the child is a fresh process tree.
  • If a safe guard can't be proven, remove the hook rather than ship a process bomb.
0.2

Live production APP_KEY is committed to the repo

Critical

.env.example is byte-identical to the live .env. Anything Crypt::-encrypted is decryptable by anyone with repo read access — including TOTP secrets, recovery codes, and Stripe secret keys stored as encrypted:array.

.env.example:3 APP_KEY=base64:Q+Qwd7iA/B1SuM59tPJEPPo4hL+ELQc3LNVV8/BjtXs= .env:3 APP_KEY=base64:Q+Qwd7iA/B1SuM59tPJEPPo4hL+ELQc3LNVV8/BjtXs= ← identical

Also committed: Mailtrap credentials, the reCAPTCHA secret, and the internal resolver key fourcornerfunding2026 — which appears in four places, including a hardcoded fallback at config/domains.php:12 and a copy-pasteable exploit curl in the SaaS routing docs.

  • Rotate all four secrets; re-encrypt affected columns before rotating APP_KEY.
  • Delete the config/domains.php:12 fallback so a missing env var fails closed instead of accepting the leaked key.
0.3

Any borrower token reaches the entire admin API

Critical

Roughly 300 endpoints sit behind auth:api with no role or permission check at all. A token issued by borrower login reaches user CRUD, role CRUD, every borrower's PII, credit profiles, invoices, payments and tenant config. Spatie's permission middleware is registered and used on zero routes.

routes/common.php:83 middleware('auth:api') ← no role gate routes/admin.php:32 ['auth:api', 'admin'] ← correct routes/borrower.php:47 ['auth:api', 'borrower'] ← correct

These compose into full account takeover plus platform-wide PII access:

LocationDefect
UserRoleController:29assignPermissions has no authz and no tenant scope — any user grants themselves every permission. The method directly above it does scope by partner.
BorrowerService:702Tenant scoping only applies when user_type is PARTNER; every other token reads any borrower. delete() has no scoping at all.
TwoFaController:352FA confirm sits outside auth and takes a bare user_id — no proof the password step passed. 2FA is the only factor, not a second one.
FileManagerService:32entity_type/entity_id taken raw from the request. Cross-tenant read and delete of loan files, bank statements, credit reports.

config/cors.php:11Origin pattern matches every origin, with supports_credentials true.

The regression guard for this whole class: one Feature test asserting a borrower token gets 403 on every v1/common/* route. Write it before the fixes, not after.

0.4

Credentials and financials exposed to logs and the public

Critical
MicroBiltService.php:57 logs client_secret in plaintext log-viewer.php:23 require_auth_in_production => false AppServiceProvider.php:103 viewApiDocs returns true unconditionally routes/common.php:80 common/weekly-summary — unauthenticated

PHASE 1

Verification layer

Next

The absence of this layer is what allowed every Phase 0 item to ship. Build it before touching anything structural.

1.1

No tests exist anywhere

High

phpunit.xml points at test directories that are empty or absent, so composer test has nothing to run. database/factories/ contains only UserFactory — factories for Borrower, FundingApplication, Invoice, Payment and Subscription are prerequisites before feature tests are even possible.

One trap: phpunit.xml configures sqlite in-memory, but the app uses MySQL-only SQL (DATE_FORMAT, CONCAT_WS, correlated DB::raw). Point tests at a real MySQL test database or they won't exercise the query layer.

  • Start with the security regressions from 0.3 — highest value per line of test written.
  • Frontends: Vitest + React Testing Library, Playwright for the money paths.
1.2

CI deploys to production with zero checks

High

Six workflows exist across the three repos. All are deploy-only, all trigger on push to stage/release, and none run tests, lint, typecheck or scanning. There is no pull-request trigger anywhere — a push to release is an unreviewed, unverified production deploy.

DefectDetail
Dead smoke testsProduction URL fallback value equals the skip condition, so the check never runs. Staging is verified; production is not.
Unguarded migrationAPI release deploy runs migrate --force with no backup and no rollback, against a database holding SSNs.
Moving action pinssh-deploy@main is a branch, not a SHA — on the step handed the production SSH key.
Key left on diskOn smoke-test failure the EC2 private key is written to the workspace; its rm only runs inside the failure branch.
1.3

strict: true is decorative — 415 errors go unreported

Medium

Both frontends set "strict": true, but build is vite build (esbuild, transpile-only) and tsc runs nowhere. Actual state: 168 errors in the borrower portal, 247 in the admin.

The causes are mechanical, not deep: allowJs is unset while 155 .jsx files exist, so every TSX→JSX import is an implicit any; @types/react v19 is installed against React 18; @types/jquery is missing. Fix those, baseline the remainder, fail CI on new errors.

PHASE 2

Data security & compliance

Regulatory

GLBA, FCRA and PCI-DSS obligations that the current code does not meet.

2.1

SSNs and bank accounts stored in plaintext

Critical

SSN, date of birth, EIN and bank account/routing numbers are unencrypted across funding_applications, funding_application_co_borrowers, credit_profile_requests (where SSN is NOT NULL), payment_method_bank_details, borrower_credit_profiles and partners.

The codebase already knows the pattern — PartnerPaymentProvider uses encrypted:array. It simply was not applied to the regulated fields. Prefer storing last_4_ssn only, as the Borrower model already does.

2.2

Raw card number and CVV capture code is committed

Critical

PaymentMethodForms.jsx in both frontends contains three forms that collect the full PAN and CVV and POST them to our own backend. They are currently dead code — only StripeForm is imported — but they are one import away from putting the platform in PCI-DSS SAQ D scope, and transmitting CVV to your own server is never permissible.

Delete both copies and the server-side raw-card branch. The live Stripe path is correct and stays.

2.3

Live secret keys are sent to the admin browser

High

Admin settings forms round-trip real secrets into React state and the DOM: Stripe secret keys, MicroBilt credentials, the OpenAI key, AWS secret key and reCAPTCHA secret. An XSS in the admin panel exfiltrates all of them in a single request.

  • Make these fields write-only — the API returns a masked stub and accepts a new value only on change.
  • Stop persisting cached_email_config to localStorage; nothing ever reads it.
2.4

Unsanitized HTML plus a token in localStorage

High

Twenty dangerouslySetInnerHTML sites, and no sanitizer in either repo. The dangerous ones render admin-authored CKEditor HTML inside the borrower portal.

Meanwhile the bearer token and full user PII are persisted to localStorage regardless of the "Remember me" checkbox — with a code comment stating so explicitly. The store's [key: string]: unknown index signature means nobody can audit what actually lands on disk. Together these two form a direct token-theft chain.

  • Add DOMPurify behind a single <SafeHtml> component covering all 20 sites.
  • Honor rememberMe, and narrow the persisted shape to the fields actually needed.
  • Add a CSP; pin and SRI the unversioned CDN scripts.
2.5

Credit reports sent to OpenAI unredacted

High

OpenAiParserService.php:40 sends full credit-report text — including SSN and date of birth — to the public OpenAI API. No redaction, no data-processing agreement referenced in the repo, no zero-retention flag set. Under GLBA and FCRA this needs a documented subprocessor agreement and disclosure, or redaction before the call.

2.6

Auth hardening is absent or silently inert

Medium
Passport tokens never expire — no tokensExpireIn call (default: 1 year) No route throttling — the login limiter is defined but attached to nothing reCAPTCHA is nullable — attackers simply omit the field Login distinguishes unknown-email from bad-password → user enumeration

The 2FA lockout settings are the sharpest: TwoFaService.php:350 reads them with config() when they are env() keys, so the configured values never apply — and the env name in code doesn't even match the one in .env.example.

PHASE 3

Structural debt

Ongoing

Not dangerous, but it is what makes every fix above cost twice what it should.

3.1

9,400 lines duplicated across the two frontends

Medium

51 files are byte-for-byte identical across the two apps, and the copies have already silently drifted — Stripe key handling differs between them. Every fix must be made twice, which is precisely how the PCI code in 2.2 ended up in both repos.

Extract in dependency order: @fch/http, @fch/auth, @fch/formatters, @fch/data, @fch/ui, then the heavy features. Start with @fch/billing and @fch/auth — where drift is already causing divergent behavior.

The same pattern exists server-side: 14 service class names exist twice under Services/Borrower/ and Services/FCH/ as near-copies.

3.2

Every user downloads a 4 MB bundle before the login form

Medium

React.lazy and Suspense appear zero times in either repo; App.jsx eagerly imports around 40 routes. The result is a single 3.8 MB (borrower) and 4.5 MB (admin) JavaScript chunk plus roughly 2 MB of CSS — FullCalendar, jQuery, Summernote and all of PrimeReact, delivered before anyone can log in.

  • Route-level React.lazy plus a manualChunks vendor split — biggest UX win per hour spent.
  • Drop ten verified-unused dependencies, and a committed 2 MB background image.
  • Add ErrorBoundaries — their absence is what turns one render throw into a white screen.
3.3

API types are hand-written and already drifted

Medium

TypeScript types are maintained by hand against 133 PHP Resource classes. All three endpoints sampled were drifted, in both directions — fields TypeScript declares that the API never sends, and real fields TypeScript hides entirely.

dedoc/scramble already produces a live spec; generate the types from it. Delete .scribe/ — it is orphaned, ten months stale, covers three endpoints, and states "This API is not authenticated."

3.4

Branch topology contradicts the documented policy

Medium
Default branch: main in the API, master in both frontends → 4 commits ahead of stage, and deploys nowhere release is 36–90 commits behind stage develop is abandoned: 377–814 commits behind, still checked out locally 52–98 remote branches per repo · 8–27 stale beyond 6 months

Also worth a quick pass: the .env.example files name Twilio variables incorrectly, so anyone copying them gets silently-broken SMS 2FA. Two Vite variables are undefined in every environment, breaking the lead payment modal in both stage and production. And the borrower portal's README is UTF-16 encoded and names the admin repo.
